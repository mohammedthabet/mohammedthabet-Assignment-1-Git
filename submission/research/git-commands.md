# Git Command Deep-Dive

## 1. Git Squash

### السيناريو

شغال على ميزة جديدة، وعملت 10 تعديلات صغيرة أثناء التطوير.

من أمثلة رسائل الـ Commit:

`WIP`

`fix`

`تعديل بسيط`

قبل فتح Pull Request أو دمج الشغل، بستخدم Squash عشان أدمج التعديلات دي في Commit واحدة واضحة ونظيفة.

مثال لرسالة الـ Commit النهائية:

`feat: add user authentication`

الهدف إن تاريخ المشروع يفضل مرتب وأسهل في القراءة والمراجعة.

Squash مش أمر مستقل في Git.

من الطرق الشائعة لتنفيذه استخدام Interactive Rebase:

`git rebase -i HEAD~10`

## 2. Git Merge vs Git Rebase

### Git Merge

لو خلصت الشغل على فرع الميزة وعايز أدمجه في الفرع الرئيسي، ممكن أستخدم Merge.

الأمر:

`git switch main`

ثم:

`git merge feature-branch`

Merge بيحافظ على تاريخ تفرع واندماج الفروع كما حدث فعليًا.

### Git Rebase

لو أنا لسه شغال على الفرع بتاعي وعايز أحدثه بآخر تغييرات موجودة في الفرع الرئيسي، ممكن أستخدم Rebase.

الأمر:

`git switch feature-branch`

ثم:

`git rebase main`

Rebase بيعيد ترتيب Commits الخاصة بفرعي فوق أحدث نسخة من main.

النتيجة إن تاريخ Commits يبقى خطي وأنظف وأسهل في المراجعة.

### الفرق

بشكل مبسط:

- Merge يحافظ على تاريخ تفرع واندماج الفروع.
- Rebase يعيد كتابة تاريخ Commits عشان يخليه خطي وأنظف.

بتجنب استخدام Rebase على Commits منشورة وبيشتغل عليها باقي أعضاء التيم، لأنه بيغير Commit History.

## 3. Git Help

### السيناريو

نسيت الخيارات المتاحة لأمر معين في Git ومحتاج أعرف طريقة استخدامه.

بدل ما أخرج من بيئة التطوير وأدور على الأمر، ممكن أستخدم Git Help.

مثلاً لو عايز أعرف تفاصيل أمر Clean:

`git help clean`

أو:

`git clean --help`

Git هيعرض دليل الاستخدام الخاص بالأمر والخيارات المتاحة ليه.

بستخدم Git Help لما أحتاج أفهم أمر معين أو أراجع طريقة استخدامه والخيارات الخاصة بيه أثناء الشغل.

## 4. Git Cherry-Pick

### السيناريو

ظهر خطأ مهم في نسخة الإنتاج، وحد من التيم عمل إصلاح للمشكلة في فرع التطوير.

لكن فرع التطوير فيه مميزات تانية لسه مش جاهزة للنشر، وبالتالي مش عايز أدمج الفرع كله.

لو الإصلاح موجود في Commit معينة، أقدر أنقل Commit دي بس للفرع الحالي باستخدام Cherry-Pick.

الأمر:

`git cherry-pick <commit-hash>`

مثال:

`git cherry-pick a84f20c`

كده أقدر أنقل تغيير محدد من فرع لفرع تاني بدون ما أدمج باقي التغييرات الموجودة في فرع التطوير.

## 5. Git Clean

### السيناريو

أثناء الشغل على المشروع ممكن تتكون ملفات أو مجلدات غير متتبعة نتيجة تجارب أو أدوات استخدمتها.

لو مش محتاج الملفات دي ومش عايز أضيفها للمشروع، ممكن أستخدم Git Clean.

قبل الحذف بعمل معاينة الأول:

`git clean -nd`

الأمر ده بيعمل Dry Run، يعني بيعرض الملفات والمجلدات اللي هيتم حذفها من غير ما يحذفها فعليًا.

بعد ما أتأكد، أستخدم:

`git clean -fd`

الأمر ده بيحذف الملفات والمجلدات غير المتتبعة.

بستخدم Git Clean بحذر، لأن الملفات غير المتتبعة اللي بيحذفها Git ممكن يكون صعب استرجاعها بعد كده.

## 6. Git Grep

### السيناريو

عندي مشروع كبير وعايز أعرف كل الأماكن اللي بتستخدم دالة معينة.

مثلاً عايز أبحث عن:

`CalculateSalary`

ممكن أستخدم:

`git grep "CalculateSalary"`

Git هيبحث داخل ملفات المشروع ويعرض الأماكن اللي ظهر فيها النص.

مثال تاني، لو عايز أبحث عن تسجيل خدمة معينة في مشروع .NET:

`git grep "AddScoped"`

بستخدم Git Grep لما أحتاج أبحث بسرعة عن نص أو اسم دالة أو Class أو أي Pattern داخل ملفات المشروع.

## 7. Git Blame

### السيناريو

لقيت سطر كود غريب في ملف معين، والسطر عامل مشكلة أو مش فاهم سبب وجوده.

مثلاً الملف:

`UserService.cs`

ممكن أستخدم:

`git blame UserService.cs`

الأمر بيعرض معلومات عن آخر Commit غيّرت كل سطر في الملف، ومنها صاحب التغيير والتاريخ ورقم Commit.

بعد ما أعرف رقم Commit، أقدر أراجع تفاصيلها باستخدام:

`git show <commit-hash>`

كده أقدر أفهم السياق اللي حصل فيه التغيير والسبب وراه قبل ما أعدل الكود.

## 8. Git Bisect

### السيناريو

الكود كان شغال كويس الأسبوع اللي فات، لكن دلوقتي ظهر خطأ جديد.

خلال الفترة دي حصل عدد كبير من Commits، ومش عارف أي واحدة فيهم سببت المشكلة.

بدل ما أجرب كل Commit واحدة واحدة، ببدأ Git Bisect:

`git bisect start`

بعدها بحدد إن النسخة الحالية فيها المشكلة:

`git bisect bad`

وبحدد Commit قديمة أعرف إن البرنامج كان شغال عندها بشكل صحيح:

`git bisect good <commit-hash>`

Git بيستخدم Binary Search عشان يختبر Commits الموجودة بين النسخة السليمة والنسخة اللي فيها المشكلة.

بعد كل اختبار، لو المشكلة مش موجودة بكتب:

`git bisect good`

ولو المشكلة موجودة بكتب:

`git bisect bad`

Git بيكرر العملية لحد ما يحدد أول Commit سببت المشكلة.

بعد الانتهاء بستخدم:

`git bisect reset`

بستخدم Git Bisect لما يظهر Regression ومحتاج أحدد بسرعة Commit اللي أدخلت المشكلة.

## 9. Git Shortlog

### السيناريو

عايز أشوف ملخص لمساهمات المطورين في المشروع خلال فترة معينة.

ممكن أستخدم:

`git shortlog`

الأمر بيجمع Commits حسب اسم صاحبها ويعرضها بشكل مختصر.

ولو عايز أشوف عدد Commits لكل شخص:

`git shortlog -sn`

مثال للنتيجة:

`25 Mohamed`

`18 Ahmed`

`10 Sara`

بستخدم Git Shortlog لما أحتاج ملخص سريع عن المساهمين وعدد Commits الخاصة بكل شخص في المشروع.

## 10. Git Prune

### السيناريو

بعد عمليات زي حذف فروع أو إعادة كتابة تاريخ المشروع، ممكن يفضل داخل قاعدة بيانات Git بعض Objects اللي مفيش أي Reference بيوصل لها.

النوع ده بنسميه:

`Unreachable Objects`

الأمر المسؤول عن حذفها هو:

`git prune`

Git Prune يعتبر أمر Low-Level بيتعامل مباشرة مع قاعدة بيانات Git الداخلية.

لكن في الاستخدام اليومي غالبًا مش بستخدمه مباشرة.

بدل كده Git عنده Garbage Collection:

`git gc`

الأمر ده بيتولى عمليات التنظيف وإدارة مساحة المستودع بطريقة أكثر أمانًا.

بالتالي Git Prune مهم لفهم طريقة التنظيف الداخلية في Git، لكن مش من الأوامر اللي المفروض أستخدمها بشكل عشوائي.

## 11. Git Worktree

### السيناريو

أنا شغال على ميزة كبيرة ولسه عندي تعديلات كثيرة مش جاهزة.

فجأة ظهر خطأ مهم في نسخة الإنتاج واتطلب مني أعمل إصلاح سريع على الفرع الرئيسي.

بدل ما أخزن التغييرات الحالية مؤقتًا وأتنقل بين الفروع، ممكن أستخدم Git Worktree.

مثلاً:

`git worktree add ../hotfix main`

الأمر ده بيفتح الفرع الرئيسي في مجلد عمل منفصل.

في نفس الوقت، يفضل شغلي الحالي موجود في المجلد الأصلي بدون ما أحتاج أغير الفرع.

ولو عايز أشوف مجلدات العمل الموجودة:

`git worktree list`

بستخدم Git Worktree لما أحتاج أشتغل على أكتر من فرع في نفس الوقت بدون التنقل المستمر بينهم أو استخدام Stash.

## 12. Git Verify-Commit

### السيناريو

شغال في مشروع بيطبق معايير أمان، والتيم بيستخدم Commits موقعة عشان يقدر يتحقق من مصدر التغييرات.

لو عايز أتحقق من توقيع Commit معينة، أستخدم:

`git verify-commit <commit-hash>`

Git بيتحقق من التوقيع الرقمي الموجود على Commit.

عشان الأمر يشتغل، لازم Commit تكون موقعة من الأساس بطريقة توقيع مدعومة.

من أمثلة طرق التوقيع:

`GPG`

أو:

`SSH Signing`

بستخدم Git Verify-Commit لما أحتاج أتأكد من صحة توقيع Commit قبل الاعتماد عليها، خصوصًا في المشاريع اللي بتطبق سياسات أمان على الكود وتاريخ المشروع.

## 13. Git Filter-Repo

### السيناريو

حد من التيم رفع بالغلط ملف فيه بيانات حساسة.

مثلاً الملف ممكن يحتوي على كلمة مرور أو Secret داخل Connection String.

حتى لو حذفنا الملف في Commit جديدة، النسخ القديمة منه ممكن تفضل موجودة في تاريخ Git.

في الحالة دي ممكن نستخدم Git Filter-Repo لإعادة كتابة تاريخ المشروع وإزالة الملف منه.

مثال:

`git filter-repo --path sensitive-file.txt --invert-paths`

الأمر ده بيعيد كتابة تاريخ المشروع ويحذف المسار المحدد من النسخ القديمة.

Git Filter-Repo أداة قوية لأنها بتعمل History Rewriting.

عشان كده لازم أستخدمها بحذر، خصوصًا لو المستودع مشترك مع باقي أعضاء التيم.

ولو البيانات اللي اتسربت كانت Password أو API Key أو أي Secret، حذفها من تاريخ Git مش كفاية.

لازم كمان ألغي أو أغير Secret المتسرب فورًا، لأن ممكن يكون حد حصل عليه قبل ما يتم حذفه.
